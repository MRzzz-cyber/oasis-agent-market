# Oasis：从 Harness 视角规划产品

状态：产品与工程规划。下面的目标能力不能视为已经实现；当前预测市场分支只接入公共市场研究、卖盘成本估计和现有 Arbitrum 兑换的充值卡片。

## 产品定位

Oasis 帮用户将一个投资意图推进到可核验的结果。对话承接意图和解释；Harness 管理上下文、工具能力、确定性约束、任务状态、钱包确认与恢复。模型可以提建议，最终可执行内容由受约束的交易适配器生成，并由用户确认。

核心使用单元是一个 Investment Intent，而不是一条聊天消息。用户离开、换模型或刷新页面后，已提交交易仍然可查，未知结果仍然阻止重复操作。

首要目标：用现有钱包完成一笔可追踪、可恢复的交易，再扩展平台数量。研究、现货兑换、预测盘口购买、赎回和提款分别声明能力与授权。

## 用户看到的流程

用户：“帮我找关于降息的预测盘口，预算最多 10 USDC，比较后我来确认。”

1. 识别研究主题、预算上限、支付资产、已有钱包和可用平台。暂时缺少支付网络时先研究，不把网络选择变成研究前置门槛。
2. 给少量候选盘口，说明关联理由、截止时间、结算规则、来源与数据时间。推荐关注度或流动性不代表预测胜率。
3. 用户选定事件与结果后，核对不同平台是否真正等价；同名或相似标题不足以直接比价。
4. 按同一预算或相同份额比较可成交深度、交易费、网络费及必要资金准备成本。未知项目保留未知，不能评选“总成本最低”。
5. 只有适配器声明可交易时，才准备用户可审阅的订单。余额不足则在当前任务卡内显示缺口、正确资产/网络、已核验收款地址与收款码。
6. 资金到账只恢复到“重新报价/待确认”，不能自动买入。切换网络是明确的钱包操作，完成后重新核验账户、余额和报价。
7. 用户确认被绑定到这一版订单；授权、签名、提交和回执进度在同一张卡片内更新。
8. 区分订单已提交、部分成交、全部成交、事件已结算和收益已赎回。购买到预测份额不代表预测获胜，也不代表资金已到账。

## Harness 的六个模块

| 模块 | 负责内容 | 不应交给模型自由决定的内容 |
| --- | --- | --- |
| Intent Store | 用户目标、预算、支付资产、当前钱包、修改版本 | 无证据增加预算、替换收款地址 |
| Context Builder | 相关对话、账户快照、事件规则、工具数据及时间 | 把网页/盘口文字当系统指令 |
| Tool Registry | 每个平台的实际能力和类型化输入输出 | 把有公开行情等同于可下单 |
| Policy Gate | 价格边界、整数金额、有效期、资产与网络、授权范围 | 任意合约调用、无限授权、跳过用户确认 |
| Task Runner | 明确状态、跨标签页锁、幂等、取消与暂停恢复 | 未知结果下自动重试或换平台再买 |
| Evidence & Evaluation | 原始订单、交易哈希、回执证据、测试与故障回放 | 用模型回答或余额变动证明成交 |

先在现有 Worker、浏览器钱包桥和小型 JS 模块内实现这些边界，不先引入多 Agent 系统。

## 状态驱动界面

研究路径：`draft → researching → candidates → comparing → preparing`。

执行路径：`preparing → awaiting_funds / awaiting_network / ready_for_review → awaiting_approval → awaiting_signature → submitting → pending → partially_filled / filled / failed`。

任何提交结果不明确时进入 `reconciliation_required`。这是一种持久阻塞状态，不因关闭提示、页面刷新、余额变化或更换模型而解除。取消本地等待也不等于撤销已提交订单。

界面由唯一任务状态生成：一张任务卡、一个主要动作、一处状态解释。研究详情和技术记录默认折叠。当前任务的错误原因进入任务卡，避免橙色警告、全局 toast 和下方回执重复描述同一问题。

## 最小数据契约

- `Intent`：id、owner、revision、goal、marketType、selectedOutcome、budgetCapAtomic、budgetAsset、walletIdentity、createdAt。
- `Evidence`：provider、resourceId、fetchedAt、sourceTimestamp、expiry、rawPayloadDigest、rulesVersion。
- `Comparison`：经过核验的 eventKey/outcomeKey、截止时间与时区、结算规则摘要、支付资产；费用未知或规则有差异时不得生成最低总成本排名。
- `ReviewedOrder`：intentId/revision、adapter/version、account、chain、marketAssetId、side、份额或支出上限、最高价格/最低到账、费用上限、expiry、reviewDigest。
- `TaskEvent`：taskId、单调递增序号、事件类型、时间、前一版本、公开证据引用。日志不记录签名、私钥、API Secret 或可重放的认证内容。
- `PendingAction`：在请求钱包或订单提交前写入意图、幂等标识和恢复所需信息；已知哈希或平台订单号立即补记。

短期复用本地交易日志和跨标签页锁。后续增加账号维度的服务端任务事件镜像，用来恢复任务和跨设备查看；服务端记录不获得钱包签名或支出权限。浏览器历史记录和交易证据的迁移分别处理。

## 适配器按能力接入

每个适配器分别声明 `search`、`rules`、`quote`、`readAccount`、`switchNetwork`、`approveExact`、`submitOrder`、`readOrder`、`cancelOrder`、`redeem`、`withdraw`。前端依据当前能力和账户状态开放按钮。

当前实现：

- Arbitrum USDC → ETH：已有钱包确认与回执核验；本分支补充充值卡片和去重状态。
- Polymarket：公共搜索与卖盘估计；签名、准确费用、协议资产核验和订单恢复仍待实现。不能沿用已停用的旧客户端或默认创建新钱包。
- Kalshi：公共市场数据；账户授权、可交易余额和订单接入仍待实现。不能以 EVM 钱包签名代替该平台授权。

平台准入应按真实用户条件核验，不能使用服务器位置代替用户资格。跨链转入、兑换抵押资产、买入和提款是不同资金动作，分别展示和确认。

## 开发顺序与验收

P0：稳定现有第一笔交易。验收钱包不变、网络正确、金额正确、回执可核验；未知结果不重复提交，提示不重复。

P1：预测市场研究卡片。验收真实数据、来源时间、盘口规则、平台故障隔离、相同份额深度估计和明确的未支持能力。当前 PR 属于这一阶段。

P2：一个预测平台的完整钱包购买闭环。先完成现有 EOA 的身份绑定、平台资格、抵押资产与网络、精确授权、用户确认、订单号和恢复；金额不足时展示对应资金卡片。不要同时承诺所有平台都支持直接钱包购买。

P3：事件等价映射和完整费用比价。只有同事件、同结果、同规则和已知总成本时，才推荐更低成本路径。

P4：增加其他平台、持仓、取消订单、赎回和提款。周期策略与代理交易在单笔交易稳定之后另设明确授权范围。

必须覆盖的故障场景：网络/钱包变化、预算修改、报价过期、市场关闭、深度不足、余额未知、网络费不足、授权取消、签名取消、提交超时、部分成交、重复点击、跨标签页并发、刷新恢复、订单与回执不匹配、平台不可用、外部内容注入。

主要指标：任务完成率、从用户选定订单到钱包确认的操作数、首笔交易完成时间、失败后恢复率、未知提交状态滞留时长、重复提交次数、错误钱包/网络/金额次数。后两项必须为零；收入和平台数量不应替代这些验收指标。
